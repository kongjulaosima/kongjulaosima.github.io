## 一、大模型应用开发（17%）

### 1.1 通过OpenAI API调用大模型

- 使用OpenAI Python SDK调用千问(Qwen)大模型，通过阿里云百炼平台
- API Key配置：存储在环境变量 `DASHSCOPE_API_KEY` 中，不要硬编码在代码里
- base_url: `https://dashscope.aliyuncs.com/compatible-mode/v1`
- 调用方式: `client.chat.completions.create(model=..., messages=...)`

### 1.2 基本API参数

| 参数 | 说明 |
|------|------|
| **model** | qwen-max, qwen-plus, qwen-turbo, qwen-long等 |
| **temperature** | 控制softmax输出概率分布的"尖锐程度"，取值范围[0, 2)，默认0.7。越低输出越确定，越高输出多样性越高 |
| **top_p** | 控制候选Token集合的采样范围，取值(0, 1]，默认0.8。值越大候选范围越广 |
| **seed** | 传入相同seed值并保持其他参数不变，模型会尽最大可能返回相同结果 |
| **max_tokens** | 控制输出长度 |
| **presence_penalty** | 提高可减少重复内容 |

- **不建议同时调整temperature和top_p**，应优先调整其中一种
- `enable_search` 参数：让大模型在生成回答时利用互联网搜索结果

### 1.3 批量生成与流式生成

**流式输出：**
- 设置 `stream=True` 参数
- 模型像打字一样一边思考一边输出，提升交互体验
- 通过 `chunk.choices[0].delta.content` 获取增量内容
- 流式输出只改变内容展示方式，不影响模型思考过程和答案质量

### 1.4 理解消息与对话历史（多轮对话）

- `messages` 参数是一个列表，包含对话完整历史记录
- 每条消息有 `role` 和 `content` 两个关键字段
- role可取: `system`(系统指令), `user`(用户输入), `assistant`(模型回复)
- **大模型API是无状态的**，每次调用都是独立的，需要手动维护messages列表
- 对话历史会占用上下文窗口空间，过多轮次需截断或摘要处理

### 1.5 推理大模型

- Qwen3等推理模型会先输出思考过程(`reasoning_content`)，再输出回答内容
- 推理模型擅长数学解题、代码编写、法律分析等需要严谨推理的场景
- 通用模型适合明确定义的通用任务，响应更快
- 可混合使用两种模型：推理模型做规划和决策，通用模型做任务执行

### 1.6 通过LlamaIndex向通义千问提问

- `SimpleDirectoryReader`: 加载指定文件夹中的文件为document对象
- `VectorStoreIndex.from_documents()`: 包含切片与建立索引步骤
- `index.as_query_engine()`: 创建查询引擎
- `index.storage_context.persist()`: 保存索引到本地
- `load_index_from_storage()`: 从本地加载索引
- `CondenseQuestionChatEngine`: 支持RAG多轮对话，通过问题改写解决上下文丢失

## 二、大模型提示词工程（15%）

### 2.1 提示词框架六要素

| 要素 | 说明 |
|------|------|
| **任务目标(Object)** | 明确要求大模型完成什么任务 |
| **上下文(Context)** | 任务的背景信息、操作流程、任务场景 |
| **角色(Role)** | 大模型扮演的角色，强调语气、写作风格 |
| **受众(Audience)** | 明确针对的特定受众，约束应答风格 |
| **样例(Sample)** | 让大模型参考的具体案例 |
| **输出格式(Output Format)** | 指定输出的格式、类型、枚举值范围 |

### 2.2 提示词分隔符

- 使用 `【】`、`<< >>`、`###` 标识关键要素
- 使用 `===`、`---` 分隔段落
- 使用xml标签 `<tag> </tag>` 对特定段落标识
- 如果提示词中已大量使用某种符号，应避免用该符号作为分隔符

### 2.3 提示词模板

- LlamaIndex默认模板: Context information + Given context answer the query
- 自定义模板中 `context_str` 和 `query_str` 是变量，分别替换为检索到的上下文和用户问题
- 提示词应可配置，方便领域专家参与设计

### 2.4 系统角色提示词的作用

- `system` role 定义大模型的行为准则、角色定位和回答规范
- 不同角色(大模型算法工程师/小学老师)对同一问题回答风格完全不同

### 2.5 提示词技巧

1. **清晰表达需求并使用分隔符**: 明确任务需求、主题、受众
2. **限定角色和受众**: 约束回答风格
3. **规定输出格式**: 要求JSON格式输出，便于下游系统解析
4. **提供少样本示例(Few-shot)**: 提供样例让大模型模仿风格和结构
5. **给模型"思考"的时间(CoT)**: 思维链方法，让模型一步步推导，提升复杂任务表现
6. **Meta Prompting**: 让大模型成为提示词教练，自动分析和优化提示词
   - 单次优化: 描述目标让AI教练生成优化版提示词
   - 多轮迭代: 引入参考答案进行差距分析，设定->生成->分析差距->优化->重复
   - 效果评测: 使用大模型作为评分员(Grader)，按友好度、结构清晰度、信息准确性打分

### 2.6 推理大模型提示词技巧

- 保持任务提示简洁清晰，提供足够背景信息
- **避免思维链提示**（推理模型本身会深入思考）
- 根据模型响应调整提示词
- 让推理模型成为"提示词教练"

### 2.7 大模型适用场景与算法应用

- **文档质量审查**: 检查错别字、语法错误、敏感信息，输出JSON格式结果
- **内容生成**: 根据主题创作教程，保持一致风格
- **批量意图分类**: 识别用户问题类型
- **文档审阅与自动修订**

## 三、大模型检索增强 RAG（20%）

### 3.1 RAG核心要素

- **RAG = Retrieval Augmented Generation（检索增强生成）**
- 核心思想: 先检索出与问题最相关的私有知识片段，与用户问题合并后传给大模型生成答案
- 两阶段: **建立索引** + **检索生成**

### 3.2 建立索引四步骤

| 步骤 | 说明 |
|------|------|
| **文档解析** | 将知识库文档加载并解析为文字形式(支持PDF/Word/Markdown等) |
| **文本分段** | 将文本进行分段，便于快速找到最相关内容 |
| **文本向量化(Embedding)** | 使用embedding模型将段落与问题数字化表示，进行相似度比较 |
| **存储索引** | 将向量化后的段落存储为向量数据库 |

### 3.3 检索生成

- **检索**: 通过embedding模型对问题进行文本向量化，与向量数据库段落进行语义相似度比较
- **生成**: 将问题与检索到的文本段通过提示词模板生成最终提示词，由大模型生成回复

### 3.4 RAG多轮对话

- 挑战: 检索时上下文丢失（如"他的主管是谁"不知道"他"指谁）
- 解决方案: **问题改写** - 利用大模型根据对话历史对当前问题改写，融入上下文信息
- LlamaIndex的 `CondenseQuestionChatEngine` 实现

### 3.5 召回优化策略

| 策略 | 说明 |
|------|------|
| **句子窗口检索** | 用小块做检索定位，返回时自动扩展到周围几句话(`SentenceWindowNodeParser`, `window_size`参数) |
| **自动合并检索** | 按层级结构组织文档，检索时从叶子节点匹配，自动合并为父节点返回完整上下文 |
| **问题改写** | 用大模型扩充用户问题，增加上下文信息 |
| **多步查询** | `StepDecomposeQueryTransform` 将复杂问题分解成多个子问题 |
| **HyDE(假设文档嵌入)** | 先让大模型编一个假想答案文档，用它来检索真实文档 |
| **标签提取增强检索** | 从文档切片中提取结构化标签，检索时先标签过滤再向量检索 |
| **重排序(Rerank)** | 先召回较多切片(如20个)，再用重排序模型(如qwen3-rerank)筛选最相关的 |

### 3.6 文本分割方法对比

| 方法 | 说明 |
|------|------|
| **Token切片** (`TokenTextSplitter`) | 按Token数量切片，适合上下文长度小的模型 |
| **句子切片** (`SentenceSplitter`) | 默认策略，保持句子完整性 |
| **句子窗口切片** (`SentenceWindowNodeParser`) | 每个切片包含周围句子作为上下文窗口 |
| **语义切片** (`SemanticSplitterNodeParser`) | 根据语义相关性自适应选择切片点 |
| **Markdown切片** (`MarkdownNodeParser`) | 按标题层级智能分割 |

### 3.7 文档解析优化

- **文档解析**: DashScopeParse支持PDF/Word解析，可提取图片中文字(OCR)
- **标题改写**: 将"注意事项"改为"需求分析>注意事项"，增加区分度
- **表格增强**: 将表格信息转换为Markdown格式，保持结构清晰

### 3.8 Embedding模型与向量数据库

**Embedding模型选择：**
- text-embedding-v3 优于 text-embedding-v2
- 更新版本的Embedding模型通常效果更好
- 余弦相似度用于衡量向量相似度

**向量数据库选择：**
| 类型 | 适用场景 |
|------|----------|
| 内存向量存储 | 适合开发测试 |
| 本地向量数据库(Milvus/Qdrant) | 功能完整，需自行部署 |
| 云服务(DashVector) | 自动扩容、按量付费、支持混合检索 |

### 3.9 RAGAS指标体系

| 指标 | 说明 |
|------|------|
| **Answer Correctness** | 评估生成答案的准确度 = 0.25 * 语义相似度 + 0.75 * 事实准确度 |
| **Answer Relevancy** | 评估生成的答案是否与问题相关 |
| **Faithfulness** | 评估生成的答案与检索到的参考资料的事实一致性（检测幻觉） |
| **Context Precision** | 评估contexts中与准确答案相关的条目是否排名靠前（信噪比） |
| **Context Recall** | 评估有多少相关参考资料被检索到 |

- 事实准确度通过大模型将answer和ground_truth分别生成观点列表，计算TP/FP/FN的F1 score

### 3.10 其他评测框架

- **TruLens**: 专注于评估可观测性，提供Groundedness/Answer Relevance/Context Relevance
- **DeepEval**: 将TDD思想引入RAG应用，支持CI/CD集成

### 3.11 Lost in the Middle现象

- 关键信息被大量无关信息淹没，大模型可能"视而不见"
- 解决: 提高上下文的"知识浓度"，减少噪音

## 四、大模型微调（16%）

### 4.1 微调的作用

- 让小模型掌握专业能力（蒸馏）
- 面向特定领域场景提升效果

### 4.2 蒸馏(Distillation)

- 用大模型(教师模型)的输出训练小模型(学生模型)
- 让小模型掌握专业能力，降低推理成本
- 微调数据集构建、参数调整、效果评测

### 4.3 文本向量化(Embedding)

- Embedding模型将文本转换为高维向量表示语义
- 对比学习: 训练时让相关文本对向量相似度高，不相关的低
- 余弦相似度用于衡量向量相似度

### 4.4 微调评测

- **BleuScore**: 基于n-gram评估响应与正确答案之间的相似性，取值0-1
- 用于评测微调带来的收益

## 五、多Agent及多模态应用（16%）

### 5.1 Agent基础概念

- **Agent = 大模型 + 工具 + 规划能力**
- 从"只会说"进化到"会做"
- 核心机制: 工具定义 -> 工具选择 -> 输出格式约束 -> 工具执行

### 5.2 Function Calling（函数调用）

1. **工具定义**: 在API的 `tools` 参数中定义可用工具，使用JSON Schema描述name/description/parameters
2. **调用决策**: 模型根据用户输入和工具定义自动决策是否调用工具，返回 `tool_calls` 字段
3. **执行与返回**: 解析tool_calls -> 执行函数 -> 将结果包装为 `role:"tool"` 的message -> 再次调用API
4. `tool_choice="auto"` 让模型自动决定是否调用工具

### 5.3 ReAct框架

- **思考(Think) -> 行动(Act) -> 观察(Observe)** 循环
- Agent观察工具调用结果，思考任务是否完成，决定回复最终答案或继续调用工具
- **AgentScope框架**: 生产级Agent框架，内置ReActAgent和工具调用逻辑
  - 开箱即用的ReAct Agent
  - 通过Toolkit类统一管理工具函数
  - 支持OpenAI/DashScope/Anthropic等主流API

### 5.4 MCP协议(Model Context Protocol)

- 核心思想: **"谁提供工具，谁定义工具"**，将工具定义职责从Agent转移到工具服务
- **MCP Server**: 工具提供方，负责声明工具(名称、描述和参数)
- **MCP Client**: 工具消费方，连接MCP Server并拉取工具定义
- 类比USB协议: 统一标准，即插即用
- 传输方式:
  - **stdio**: 本地开发调试，Claude Desktop/Cursor等IDE集成
  - **Streamable HTTP**: 远端部署，多Agent/多用户共用

### 5.5 Agent规划与执行

**反思(Reflection)两种模式：**
- 自我反馈(Self Review): 单步指令式反思 / 两步式"生成-反馈"
- 外部反馈(External Feedback): 把生成结果放到真实环境执行，根据执行结果迭代修正

**工作流编排五种模式：** 流水线、分支、并行、MoA(混合Agent)、人机协作

**Plan & Execute**: Agent先规划再执行，代码即计划

### 5.6 多Agent协作模式

**分层规划模式(Leader-Worker)：**
- Leader Agent接收顶层任务，分解为子任务分派给Member Agents
- 使用handoff机制实现
- 结构清晰、权责分明，每个子代理拥有独立上下文窗口
- 适合目标明确、可清晰分解为并行子任务的场景

**共创协作模式(Blackboard)：**
- 去中心化，围绕共享白板进行头脑风暴
- 使用MsgHub实现，任何Agent的回复自动被其他参与者"听到"
- 适合没有唯一正确答案的开放性、创造性问题
- 风险: 讨论发散无法收敛、成本高(3-5倍Token消耗)

### 5.7 Memory（记忆机制）

- **短期记忆**: 当前对话上下文
- **长期记忆**: 跨会话的经验积累
- **主动记忆管理**: Agent主动整理和存储经验
- 解决"每次新任务像失忆"的问题

### 5.8 Skill（技能固化）

- 将能力固化为可复用流程
- 从Prompt到Skill的演进
- 好的工作方法不应停留在聊天记录里，应固化为可复用流程

### 5.9 评测驱动Agent开发

- 端到端评测 + 白盒化评测
- 缺少系统化方法判断Agent干得好不好，需要从"偶尔对"变成"持续对"

## 六、生产环境应用实践（16%）

### 6.1 云上部署方案

| 服务 | 说明 |
|------|------|
| **阿里云百炼平台** | 提供可视化大模型应用构建能力 |
| **ECS** | 弹性计算服务 |
| **FC(函数计算)** | 发布AI助手 |
| **PAI** | 机器学习平台 |
| **百炼** | 大模型服务平台，提供提示词自动优化、可视化工作流、智能体编排 |

### 6.2 vLLM部署

- 高性能大模型推理引擎
- 用于在云上部署微调模型

### 6.3 性能与成本平衡

- 使用**上下文缓存(Context Cache)**: 缓存命中部分按标准单价20%计费
- 选择合适规模的模型（小任务用小模型）
- 多Agent系统的成本意识（3-5倍Token消耗）
- "生成-反馈"循环: 让中端模型达到顶级模型95%效果

### 6.4 稳定性保障

- **结构化输出**: 使用JSON Schema定义输出结构，Pydantic验证
- **"引导-校验-重试"闭环**: 定义结构 -> 构建提示词 -> 校验与重试
- **避免幻觉**: 通过提示词要求大模型不编造答案

### 6.5 安全合规

- API Key安全: 存储在环境变量中，不要硬编码
- 生产环境中不要将API Key输出到日志
- 领域专家深度参与评测系统
- 评测先行的优化策略: 明确业务目标 -> 构建评测集 -> 建立自动化评测 -> 针对性优化 -> 评测验证 -> 持续迭代

### 6.6 评测运营体系

- 构建高质量评测集: 问题来自真实用户场景，标准答案由业务领域专家提供
- 业务指标与评测指标对齐: 算法指标是手段，业务指标才是目标
- 持续运营: 发现问题 -> 改进优化 -> 跟踪效果 -> 迭代指标

### 6.7 意图空间与知识空间

- **重叠区域**: 依靠知识库回答用户问题，通过优化内容质量和工程算法提升
- **未被覆盖的意图空间**: 主动补充缺漏知识
- **未被利用的知识空间**: 优化召回算法，剔除无关内容

## 七、其他重要知识点

### 7.1 上下文工程(Context Engineering)

- 专注于为大模型的上下文窗口填充恰到好处的信息
- 核心技术: RAG、Prompt(提示词工程)、Tool(工具使用)、Memory(记忆机制)
- 许多大模型应用的失败并非模型不够智能，而是"上下文"的失败

### 7.2 GraphRAG

- 结合RAG和查询聚焦摘要(QFS)
- RAG擅长精确细节，QFS善于理解总结整体内容

### 7.3 大模型工作流程

1. 文本分词(Tokenization)
2. Token向量化(Embedding矩阵 + 位置信息)
3. 大模型推理(Transformer解码器层 -> 隐藏状态向量 -> 分数向量Logits)
4. 解码与自回归(softmax概率分布 -> 解码策略选择Token)
5. 输出文本(流式输出)

### 7.4 解码策略

- **近似确定性解码**: 贪心解码、Beam Search
- **随机采样解码**: Top-p(Nucleus Sampling)、Top-k Sampling
