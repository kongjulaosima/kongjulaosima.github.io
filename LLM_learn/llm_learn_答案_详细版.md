## 一、大模型应用开发（17%）

### 1.1 如何通过OpenAI API调用大模型？

**答：** 使用OpenAI Python SDK调用通义千问(Qwen)大模型，通过阿里云百炼平台提供的兼容接口。

**关键配置：**
- `base_url`: `https://dashscope.aliyuncs.com/compatible-mode/v1`
- API Key存储在环境变量 `DASHSCOPE_API_KEY` 中，**绝对不能硬编码在代码里**
- 调用方式: `client.chat.completions.create(model=..., messages=...)`

**代码示例：**
```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1"
)

completion = client.chat.completions.create(
    model="qwen-max",
    messages=[
        {"role": "system", "content": "你是一个客服助手"},
        {"role": "user", "content": "你好"}
    ]
)
print(completion.choices[0].message.content)
```

**messages参数的三种角色：**
| 角色 | 作用 |
|------|------|
| `system` | 设置模型行为准则、角色定位和回答规范 |
| `user` | 用户输入的问题 |
| `assistant` | 模型之前的回复（用于多轮对话） |

### 1.2 大模型的基本API参数有哪些？各自的作用是什么？

**答：**

| 参数 | 说明 | 取值范围 |
|------|------|----------|
| **model** | 指定使用的模型 | qwen-max, qwen-plus, qwen-turbo, qwen-long等 |
| **temperature** | 控制softmax输出概率分布的"尖锐程度"。越低输出越确定，越高输出多样性越高 | [0, 2)，默认0.7 |
| **top_p** | 控制候选Token集合的采样范围（核采样）。值越大候选范围越广 | (0, 1]，默认0.8 |
| **top_k** | 从概率最高的top_k个Token中采样。top_k=1表示总是选最可能的Token | 正整数 |
| **seed** | 传入相同seed值并保持其他参数不变，模型会尽最大可能返回相同结果（但不能完全保证） | 整数 |
| **max_tokens** | 控制输出长度 | 正整数 |
| **presence_penalty** | 提高可减少重复内容 | [-2.0, 2.0] |
| **enable_search** | 让大模型在生成回答时利用互联网搜索结果 | true/false |

**重要注意事项：**
- **不建议同时调整temperature和top_p**，应优先调整其中一种
- temperature和top_p的工作原理不同：temperature改变整个概率分布的形状，top_p截断候选集合
- 实验表明：temperature=0时输出最稳定，temperature=1.5时输出最具创造性

### 1.3 什么是批量生成与流式生成？如何实现？

**答：**

**流式输出(Streaming)：**
- 设置 `stream=True` 参数
- 模型像打字一样一边思考一边输出，用户可以即时看到部分结果，大幅提升交互体验
- 通过 `chunk.choices[0].delta.content` 获取增量内容
- **流式输出只改变内容展示方式，不影响模型思考过程和答案质量**

**代码示例：**
```python
stream = client.chat.completions.create(
    model="qwen-max",
    messages=[{"role": "user", "content": "你好"}],
    stream=True
)
for chunk in stream:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="")
```

### 1.4 如何理解消息与对话历史（多轮对话）？

**答：**

- `messages` 参数是一个列表，包含对话的完整历史记录
- 每条消息有 `role`（角色）和 `content`（内容）两个关键字段
- **大模型API是无状态的**——每次调用都是独立的，模型不会记住之前的对话
- 要实现多轮对话，必须在每次调用时手动维护并传入完整的messages列表
- 对话历史会占用上下文窗口空间，过多轮次会导致：推理变慢、成本增加、注意力稀释

**多轮对话实现方式：**
```python
conversation_history = []

def chat(user_message):
    conversation_history.append({"role": "user", "content": user_message})
    response = client.chat.completions.create(
        model="qwen-max",
        messages=conversation_history
    )
    assistant_message = response.choices[0].message.content
    conversation_history.append({"role": "assistant", "content": assistant_message})
    return assistant_message
```

### 1.5 大语言模型的工作原理是什么？

**答：** 大语言模型的工作流程分为5个阶段：

| 阶段 | 名称 | 说明 |
|------|------|------|
| 1 | 文本分词(Tokenization) | 将输入文本切分为Token（子词或字符片段），每个Token映射为词表中的整数ID |
| 2 | Token向量化(Embedding) | 通过Embedding矩阵将Token ID转换为稠密向量，加上位置编码让模型理解词序 |
| 3 | 模型推理(Transformer) | 向量经过多层Transformer解码器（因果自注意力 + 前馈网络），最终隐藏状态投影为覆盖整个词表的Logits向量 |
| 4 | 解码与自回归生成 | Logits经softmax转为概率分布，解码策略选择下一个Token，选中的Token拼接到输入末尾，重复此过程直到遇到结束符 |
| 5 | 输出文本 | Token ID转换回人类可读文本。流式输出则逐个Token发送 |

**解码策略分类：**
- **近似确定性解码**：贪心解码（总是选概率最高的）、Beam Search（保留多个候选序列）
- **随机采样解码**：Top-p/Nucleus Sampling（按累积概率截断候选集）、Top-k Sampling（从概率最高的k个Token中采样）

### 1.6 推理大模型与通用大模型有什么区别？

**答：**

| 维度 | 推理模型（如Qwen3） | 通用模型 |
|------|---------------------|----------|
| 设计目标 | 逻辑推理、多步问题求解 | 通用对话、知识问答、文本生成 |
| 输出特点 | 完整的推导步骤和逻辑链 | 简洁、直接、结果导向 |
| 响应速度 | 较慢（多步计算） | 较快（单步生成） |
| 擅长场景 | 数学解题、代码编写、法律分析 | 明确定义的通用任务 |

**推理模型的特殊机制：**
- 会先输出思考过程（`reasoning_content`），再输出回答内容
- 类似于在草稿纸上解数学题

**最佳实践：**
- 可混合使用两种模型：推理模型做规划和决策，通用模型做任务执行
- 使用推理模型时应避免显式的思维链(CoT)提示——模型本身就会深入思考，强制CoT可能限制它

### 1.7 如何通过LlamaIndex构建RAG应用？

**答：**

**核心组件：**
| 组件 | 作用 |
|------|------|
| `SimpleDirectoryReader` | 加载指定文件夹中的文件为document对象 |
| `VectorStoreIndex.from_documents()` | 包含切片与建立索引两个步骤 |
| `index.as_query_engine()` | 创建查询引擎 |
| `index.storage_context.persist()` | 保存索引到本地磁盘 |
| `load_index_from_storage()` | 从本地加载索引（比重新构建快得多） |
| `CondenseQuestionChatEngine` | 支持RAG多轮对话，通过问题改写解决上下文丢失 |

**基本流程：**
```python
from llama_index.core import SimpleDirectoryReader, VectorStoreIndex

# 加载文档
documents = SimpleDirectoryReader('./docs').load_data()
# 创建索引（自动完成切片和向量化）
index = VectorStoreIndex.from_documents(documents, embed_model=...)
# 创建查询引擎
query_engine = index.as_query_engine(streaming=True, llm=...)
# 提问
response = query_engine.query("公司年假政策是什么？")
```

**RAG多轮对话的挑战与解决方案：**
- **问题**：后续问题常缺少上下文（如"他的主管是谁"——"他"指谁？）
- **解决方案**：问题改写——利用大模型根据对话历史将当前问题改写为独立完整的问题
- LlamaIndex的 `CondenseQuestionChatEngine` 自动实现此功能

### 1.8 什么是上下文工程(Context Engineering)？

**答：**

上下文工程是一门专注于为大模型的上下文窗口填充恰到好处信息的学科。

**核心技术：**
- **RAG**（检索增强生成）
- **Prompt**（提示词工程）
- **Tool**（工具使用）
- **Memory**（记忆机制）

**关键洞察：** 许多大模型应用的失败并非模型不够智能，而是"上下文"的失败。上下文窗口就像计算机的RAM——容量有限，需要精心管理。

**直接注入知识的局限性：**
- 少量知识可以直接写入system prompt
- 但上下文窗口有限，大量知识会导致：推理变慢、成本增加、信息干扰（无关内容分散模型注意力）

## 二、大模型提示词工程（15%）

### 2.1 提示词框架的六要素是什么？

**答：**

| 要素 | 英文 | 说明 | 示例 |
|------|------|------|------|
| **任务目标** | Object | 明确要求大模型完成什么任务 | "审查以下课程文档的质量" |
| **上下文** | Context | 任务的背景信息、操作流程、任务场景 | "这是一份面向新员工的Python入门课程" |
| **角色** | Role | 大模型扮演的角色，强调语气、写作风格 | "你是一位资深课程评审专家" |
| **受众** | Audience | 明确针对的特定受众，约束应答风格 | "目标受众是零基础的编程初学者" |
| **样例** | Sample | 让大模型参考的具体案例 | 提供一个评审好的文档示例 |
| **输出格式** | Output Format | 指定输出的格式、类型、枚举值范围 | "以JSON格式输出，包含label、reason、correct三个字段" |

---

### 2.2 提示词分隔符有哪些？如何使用？

**答：**

**常用分隔符类型：**
| 类型 | 示例 | 用途 |
|------|------|------|
| 符号标记 | `【】`、`<< >>`、`###` | 标识关键要素 |
| 段落分隔 | `===`、`---` | 分隔不同段落 |
| XML标签 | `<tag> </tag>` | 对特定段落标识 |

**使用原则：**
- 如果提示词中已大量使用某种符号，应避免用该符号作为分隔符
- 分隔符帮助模型解析提示词结构，避免不同部分之间的混淆

### 2.3 什么是提示词模板？如何自定义？

**答：**

提示词模板是将提示词中的固定部分（角色、约束条件）预先设定，将输入参数作为变量的机制。

**LlamaIndex默认RAG模板：**
```
Context information is below.
---------------------
{context_str}
---------------------
Given the context information and not prior knowledge, answer the query.
Query: {query_str}
Answer:
```

其中 `{context_str}` 和 `{query_str}` 是变量，分别替换为检索到的上下文和用户问题。

**自定义模板示例：**
```python
from llama_index.core import PromptTemplate

template = (
    "你是公司的客服助手。请根据以下参考资料回答用户问题。\n"
    "如果参考资料中没有相关信息，请直接说"我无法回答这个问题"。\n"
    "不要编造答案。\n\n"
    "参考资料：\n{context_str}\n\n"
    "用户问题：{query_str}"
)
prompt = PromptTemplate(template)
rag.update_prompt_template(prompt)
```

**关键原则：** 提示词应可配置，方便领域专家参与设计，而非由开发者硬编码。

---

### 2.4 系统角色提示词(system role)有什么作用？

**答：**

`system` role 用于定义大模型的行为准则、角色定位和回答规范。它在对话开始时设置，影响模型在整个对话中的表现。

**对比示例：**
- 角色为"大模型算法工程师"时，回答会使用专业术语、引用论文
- 角色为"小学老师"时，回答会使用通俗语言、生活化比喻

同一个问题"什么是大语言模型"，不同角色的回答风格完全不同。system prompt是控制模型行为最有效的手段之一。

### 2.5 提示词的核心技巧有哪些？

**答：**

| 技巧 | 说明 | 适用场景 |
|------|------|----------|
| **清晰表达需求并使用分隔符** | 明确任务需求、主题、受众，用分隔符区分不同部分 | 所有场景 |
| **限定角色和受众** | 约束回答风格、深度和用词 | 需要特定风格的场景 |
| **规定输出格式** | 要求JSON等结构化输出，便于下游系统解析 | 需要程序处理结果的场景 |
| **提供少样本示例(Few-shot)** | 提供样例让大模型模仿风格和结构 | 需要一致输出格式的场景 |
| **思维链(CoT)** | 让模型一步步推导，提升复杂任务表现 | 数学推理、逻辑分析等复杂任务 |
| **Meta Prompting** | 让大模型成为提示词教练，自动分析和优化提示词 | 提示词迭代优化 |

**思维链(CoT)详解：**
- 指令："请一步步推导，给出你的推理过程"
- 效果：模型在简单prompt下可能做错的数学题，使用CoT后可以正确解答
- 原因：显式的推理步骤迫使模型展开中间计算，而非直接跳到结论

**Meta Prompting工作流：**
1. 编写初始提示词
2. 运行并观察不理想的输出
3. 构造"元提示词"：包含初始提示词、其输出、你的期望，让大模型重写提示词
4. 使用优化后的提示词

**进阶——引入参考答案的迭代优化：**
- 用当前提示词生成答案
- 与参考答案对比（由LLM"评审员"进行差距分析）
- 基于差距报告优化提示词
- 重复直到差距缩小或达到最大迭代次数

**构建"AI评审员"：**
1. 准备标注样本（好/坏答案）
2. 划分训练集/评估集
3. 迭代：在训练集上评估，找到误判案例，用Meta Prompting改进评审提示词
4. 监控训练集和评估集准确率以检测过拟合

### 2.6 推理大模型的提示词技巧有什么不同？

**答：**

| 技巧 | 说明 |
|------|------|
| 保持简洁清晰 | 提供足够背景信息，但不要过度冗长 |
| **避免显式思维链提示** | 推理模型本身会深入思考，强制CoT反而可能限制它 |

| 混合使用两种模型 | 推理模型做规划和分析，通用模型做任务执行 |

### 2.7 大模型有哪些适用的算法应用场景？

**答：**

| 场景 | 说明 | 输出格式 |
|------|------|----------|
| **文档质量审查** | 检查错别字、语法错误、敏感信息 | JSON: `{label, reason, correct}` |

## 三、大模型检索增强 RAG（20%）

### 3.1 RAG的核心思想是什么？

**答：**

**RAG = Retrieval Augmented Generation（检索增强生成）**

核心思想：先检索出与问题最相关的私有知识片段，与用户问题合并后传给大模型生成答案。

**为什么需要RAG：**
- 大模型只了解公开训练数据，无法回答公司内部问题
- 直接将全部知识塞入上下文窗口不可行（窗口有限、成本高、信息干扰）
- RAG避免了上下文窗口溢出，同时确保模型获得相关背景信息

**两个阶段：**
1. **建立索引**（离线）：文档解析 → 文本分段 → 文本向量化 → 存储索引
2. **检索生成**（在线）：问题向量化 → 相似度检索 → 拼接提示词 → 大模型生成答案

---

### 3.2 建立索引的四个步骤分别是什么？

**答：**

| 步骤 | 说明 | 关键技术 |
|------|------|----------|
| **文档解析** | 将知识库文档加载并解析为文字形式 | 支持PDF/Word/Markdown等格式，DashScopeParse支持OCR提取图片文字 |
| **文本分段** | 将文本进行分段，便于快速找到最相关内容 | Token切片、句子切片、语义切片、Markdown切片等多种方法 |
| **文本向量化(Embedding)** | 使用embedding模型将段落与问题数字化表示 | text-embedding-v3优于v2，余弦相似度衡量向量相似度 |
| **存储索引** | 将向量化后的段落存储为向量数据库 | 内存存储（开发测试）、本地DB（Milvus/Qdrant）、云服务（DashVector） |

---

### 3.3 检索生成阶段是如何工作的？

**答：**

**检索阶段：**
1. 通过embedding模型对用户问题进行文本向量化
2. 将问题向量与向量数据库中的段落向量进行语义相似度比较（余弦相似度）
3. 返回最相关的top_k个段落
4. **检索质量是RAG性能的最关键因素**

**生成阶段：**
1. 将检索到的文本段与用户问题通过提示词模板拼接
2. 典型模板：`请根据以下信息回答用户问题：{检索到的段落}。用户问题：{问题}。`
3. 由大模型生成最终回复

---

### 3.4 RAG多轮对话的挑战是什么？如何解决？

**答：**

**挑战：** 后续问题常缺少上下文。例如：
- 第一轮："张伟是谁？"
- 第二轮："他的主管是谁？"——"他"指谁？单独用这个问题检索会失败

**两种方案的对比：**
| 方案 | 问题 |
|------|------|
| 只用最新问题检索 | 缺少上下文，检索不准确 |
| 用完整对话历史检索 | 文本过长，Embedding模型性能下降 |

**解决方案——问题改写：**
- 利用大模型根据对话历史将当前问题改写为独立完整的问题
- "他的主管是谁？" → "张伟的主管是谁？"
- LlamaIndex的 `CondenseQuestionChatEngine` 自动实现此功能

### 3.5 有哪些召回优化策略？

**答：**

#### 检索前优化(Pre-retrieval)：

| 策略 | 说明 |
|------|------|
| **问题改写(Query Rewriting)** | 用大模型将模糊问题改写为完整、无歧义的问题 |
| **问题扩展(Query Expansion)** | 添加相关概念，扩大检索范围 |
| **用户画像扩展** | 将用户角色/部门信息融入查询 |
| **标签提取增强检索** | 从文档切片中提取结构化标签，检索时先标签过滤再向量检索 |
| **追问澄清** | 当问题模糊时，让大模型先追问再检索 |
| **多步查询分解** | `StepDecomposeQueryTransform` 将复杂问题分解成多个子问题 |
| **HyDE(假设文档嵌入)** | 先让大模型编一个假想答案文档，用它来检索真实文档。假想文档虽是编造的，但结构与真实文档相似，可提升检索准确度 |

#### 检索后优化(Post-retrieval)：

| 策略 | 说明 |
|------|------|
| **重排序(Rerank)** | 先召回较多切片(如20个)，再用重排序模型(如qwen3-rerank)筛选最相关的。可结合相似度阈值过滤低相关性结果 |
| **句子窗口检索** | 用小块做检索定位，返回时自动扩展到周围几句话(`SentenceWindowNodeParser`, `window_size`参数) |
| **自动合并检索** | 按层级结构组织文档，检索时从叶子节点匹配，自动合并为父节点返回完整上下文 |

---

### 3.6 有哪些文本分割方法？各自适用于什么场景？

**答：**

| 方法 | 类 | 说明 | 适用场景 |
|------|------|------|----------|
| **Token切片** | `TokenTextSplitter` | 按固定Token数量切片 | 上下文长度小的模型 |
| **句子切片** | `SentenceSplitter` | 保持句子完整性（默认策略） | 通用场景，最佳起点 |
| **句子窗口切片** | `SentenceWindowNodeParser` | 每个切片包含周围句子作为上下文窗口 | 需要保持上下文的长文档 |
| **语义切片** | `SemanticSplitterNodeParser` | 根据语义相关性自适应选择切片点 | 逻辑密集、专业内容 |
| **Markdown切片** | `MarkdownNodeParser` | 按标题层级智能分割 | Markdown结构化文档 |

**句子窗口检索的核心思想：**
解决了小块（精确匹配）和大块（完整上下文）之间的矛盾——用小块做检索，但返回时自动扩展上下文窗口。

---

### 3.7 文档解析有哪些优化方法？

**答：**

| 问题 | 解决方案 |
|------|----------|
| 不支持的文档格式 | 开发解析器或转换格式 |
| 嵌入的表格、图片、视频 | 改进文档解析器（DashScopeParse支持OCR） |
| 各章节主题相似 | 扩展标题，添加元数据标签 |
| 切片太大（噪音多） | 减小切片大小 |
| 切片太小（信息截断） | 增大切片大小 |

**具体优化技术：**
- **PDF解析**：DashScopeParse使用阿里云文档智能服务，支持从PDF/Word中提取结构化文字，包括OCR
- **标题改写**：将"注意事项"改为"需求分析>注意事项"，增加区分度
- **表格增强**：将表格信息转换为Markdown格式，保持结构清晰
- **Markdown润色**：PDF转Markdown后，用大模型修复格式问题（标题层级、表格不一致、缺失信息）

### 3.8 Embedding模型与向量数据库如何选择？

**答：**

**Embedding模型选择：**
- text-embedding-v3 优于 text-embedding-v2
- 更新版本的Embedding模型通常效果更好
- 单独升级Embedding模型就能显著提升检索质量
- 余弦相似度是衡量向量相似度的标准指标

**向量数据库选择：**

| 类型 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 内存向量存储 | 快速搭建，无需配置 | 无持久化，受内存限制 | 开发测试 |
| 本地向量数据库(Milvus/Qdrant) | 持久化，高效检索 | 需自行部署 | 小规模生产 |
| 云服务(DashVector) | 自动扩容、监控、混合检索 | 供应商依赖 | 生产环境 |

### 3.9 RAGAS指标体系包含哪些指标？如何计算？

**答：**

| 指标 | 说明 | 计算方式 |
|------|------|----------|
| **Answer Correctness** | 评估生成答案的准确度 | = 0.25 × 语义相似度 + 0.75 × 事实准确度 |
| **Answer Relevancy** | 评估生成的答案是否与问题相关 | LLM评估 |
| **Faithfulness** | 评估生成的答案与检索到参考资料的事实一致性（检测幻觉） | LLM评估 |
| **Context Precision** | 评估contexts中与准确答案相关的条目是否排名靠前（信噪比） | 逐条计算运行精确率 |
| **Context Recall** | 评估有多少相关参考资料被检索到 | LLM将ground_truth分解为陈述，检查每条是否有证据 |

**事实准确度计算细节：**
- 用大模型将answer和ground_truth分别生成观点列表
- 计算TP（正确命中的观点）、FP（answer中有但ground_truth没有的）、FN（ground_truth中有但answer没有的）
- 计算F1 score

---

### 3.10 Lost in the Middle现象是什么？如何解决？

**答：**

**现象：** 关键信息被大量无关信息淹没时，大模型可能"视而不见"。模型对输入开头和结尾的内容记忆更好，中间部分容易被忽略。

**解决方法：** 提高上下文的"知识浓度"，减少噪音。具体措施：
- 优化文本分割，减少无关内容
- 使用重排序(Rerank)将最相关内容排在前面
- 合理设置检索数量，不要返回过多切片

---

### 3.11 RAG各阶段的优化方向是什么？

**答：**

**基于RAGAS指标的优化诊断：**

| 指标表现 | 问题所在 | 优化方向 |
|----------|----------|----------|
| Context Recall低 | 检索阶段遗漏 | 检查知识库完整性、升级Embedding模型、问题改写 |
| Context Precision低 | 检索阶段噪音多 | 同上 + 添加ReRank重排序 |
| Answer Correctness低但Context指标高 | 生成阶段问题 | 优化提示词、调整模型参数、换更强模型、微调 |

**核心原则：** Context是RAG的命脉——上下文质量直接决定了RAG性能的上限。

## 四、大模型微调（16%）

### 4.1 微调的作用和前提是什么？

**答：**

**微调的作用：**
- 让小模型掌握专业能力（蒸馏）
- 面向特定领域场景提升效果
- 降低推理成本（小模型替代大模型API）

**适用场景（蒸馏的前提条件）：**
- 输出格式固定（如JSON Schema）
- 不依赖实时外部知识
- 调用频率高（成本敏感）
- 教师模型表现稳定

---

### 4.2 什么是蒸馏(Distillation)？有哪些蒸馏路径？

**答：**

**核心区别：** 微调使用人工标注数据，蒸馏使用教师模型生成的数据。

**三种蒸馏路径：**

| 路径 | 说明 | 要求 |
|------|------|------|
| **数据合成蒸馏（黑盒）** | 使用教师模型API生成标注数据 | 只需API访问权限，不需要教师权重 |
| **知识蒸馏KD（白盒）** | 学生模型学习教师模型的概率分布（软标签） | 需要教师权重，精度更高 |
| **推理压缩** | 学生模型学习教师模型的思维链轨迹 | DeepSeek-R1用此方法将671B的800K推理轨迹蒸馏到7B模型 |

**数据合成蒸馏的三步流水线：**
1. 生成多样化的查询
2. 教师模型标注（生成JSON格式的标签）
3. 质量过滤 + 格式化为训练数据

---

### 4.3 蒸馏的评测指标有哪些？

**答：**

| 指标 | 说明 |
|------|------|
| **JSON合规率** | 输出能否被解析为有效JSON且包含所有必需字段 |
| **intents F1** | 多标签意图识别的F1分数（精确率 + 召回率） |
| **route准确率** | 路由决策是否正确 |

**蒸馏效果对比（以意图识别任务为例）：**

| 指标 | 基座模型(0.6B) | 教师模型(qwen3.6-plus) | 蒸馏后(0.6B) |
|------|----------------|------------------------|---------------|
| JSON合规率 | 48% | 100% | 100% |
| intents F1 | 23.7% | 83.9% | 70.4% |
| route准确率 | 16% | 90% | 77% |

---

### 4.4 什么是LoRA微调？为什么使用LoRA？

**答：**

**LoRA (Low-Rank Adaptation) 原理：**
- 不更新所有权重，而是附加两个小的低秩矩阵 A(d×r) 和 B(r×d) 来学习变化量 ΔW = A×B
- 以d=4096, r=8为例：参数从16.7M减少到65K（仅占原始参数的0.4%）
- 保留97%以上的基座模型能力

**训练状态判断：**

| Train Loss | Eval Loss | 状态 | 操作 |
|------------|-----------|------|------|
| 不下降 | 不下降 | 训练失败 | 检查数据和配置 |
| 下降 | 下降 | 欠拟合 | 继续训练 |
| 下降 | 先降后升 | 过拟合 | 停止训练 |
| 稳定 | 稳定 | 训练成功 | 完成 |

**关键训练参数调优：**
- `lora_rank`：<200样本用4，中等复杂度用8，>2000样本用16
- `learning_rate`：默认5e-5；loss不下降可升至1e-4；loss震荡可降至1e-5
- `num_train_epochs`：eval loss上升时减少；仍在下降时增加

---

### 4.5 蒸馏的成本收益如何分析？

**答：**

**场景：** 20K请求/天，200输入Token，100输出Token

| 方案 | 日成本 | 月成本 |
|------|--------|--------|
| API调用(qwen-plus) | ~32元 | ~960元 |
| 蒸馏模型(GPU 8小时) | ~28.8元 | ~864元 |
| 蒸馏模型(GPU 24小时) | ~86.4元 | ~2592元 |

**盈亏平衡点：**
- 8小时部署：~18K请求/天
- 24小时部署：~54K请求/天

**蒸馏的非成本优势：**
- 本地延迟~50ms vs API延迟~500ms
- 数据安全（数据不出本地）
- 离线可用
- 不依赖外部服务可用性

**合规注意事项：** 开源模型(Qwen, Apache 2.0)可自由用作教师。商业模型(GPT-4, Claude)可能禁止用其输出训练竞争模型。

### 4.6 文本向量化(Embedding)的原理是什么？

**答：**

- Embedding模型将自然语言转换为高维向量，语义相似的文本产生相似的向量
- 余弦相似度用于衡量向量相似度
- **对比学习**：训练时让相关文本对向量相似度高，不相关的低
- 索引阶段：n个切片变成n个向量存储在向量数据库中
- 检索阶段：问题变成向量，检索最相似的向量及其对应的切片

## 五、多Agent及多模态应用（16%）

### 5.1 什么是Agent？Agent的核心公式是什么？

**答：**

**Agent = 大模型 + 工具 + 规划能力**

Agent从"只会说"进化到"会做"——从"顾问"变成"助手"。

**核心机制：**
1. 工具定义（告诉模型有哪些工具可用）
2. 工具选择（模型决定调用哪个工具）
3. 输出格式约束（确保模型输出可解析的调用指令）
4. 工具执行（代码执行工具函数，将结果返回模型）

---

### 5.2 Function Calling（函数调用）的工作流程是什么？

**答：**

Function Calling是业界标准的工具调用方式，由主流LLM提供商（OpenAI、Anthropic、Google、阿里云）内置支持。

**三个阶段：**

| 阶段 | 说明 |
|------|------|
| **1. 工具定义** | 在API的 `tools` 参数中定义可用工具，使用JSON Schema描述name/description/parameters |
| **2. 调用决策** | 模型根据用户输入和工具定义自动决策是否调用工具，返回 `tool_calls` 字段 |
| **3. 执行与返回** | 解析tool_calls → 执行函数 → 将结果包装为 `role:"tool"` 的message → 再次调用API获取最终回答 |

`tool_choice="auto"` 让模型自动决定是否调用工具。

**代码示例：**
```python
tools = [{
    "type": "function",
    "function": {
        "name": "web_search",
        "description": "搜索互联网获取最新信息",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "搜索关键词"}
            },
            "required": ["query"]
        }
    }
}]

response = client.chat.completions.create(
    model="qwen-max",
    messages=[{"role": "user", "content": "今天天气怎么样？"}],
    tools=tools,
    tool_choice="auto"
)
```

---

### 5.3 什么是ReAct框架？

**答：**

**ReAct = Reasoning + Acting**

核心循环：**思考(Think) → 行动(Act) → 观察(Observe)**

1. Agent观察工具调用结果
2. 思考任务是否完成
3. 决定回复最终答案或继续调用工具

**AgentScope框架**提供开箱即用的 `ReActAgent`：
- 更简洁的工具定义（只需写Python函数+docstring）
- 自动解析tool_calls
- 自动管理对话历史
- 支持多轮工具调用和异步

---

### 5.4 什么是MCP协议(Model Context Protocol)？

**答：**

**核心思想：** "谁提供工具，谁定义工具"——将工具定义职责从Agent转移到工具服务。

| 组件 | 说明 |
|------|------|
| **MCP Server** | 工具提供方，负责声明工具（名称、描述和参数） |
| **MCP Client** | 工具消费方，连接MCP Server并拉取工具定义 |

**类比：** Function Calling像内部总线；MCP像USB接口——统一标准，即插即用。

**两种传输方式：**
| 方式 | 适用场景 | 示例 |
|------|----------|------|
| **stdio** | 本地开发调试 | Claude Desktop、Cursor等IDE集成 |
| **Streamable HTTP** | 远端部署，多Agent/多用户共用 | 阿里云DashScope WebSearch MCP服务 |

---

### 5.5 Agent的反思(Reflection)机制有哪些模式？

**答：**

#### 自我反馈(Self Review)：

| 模式 | 优点 | 缺点 |
|------|------|------|
| 单步指令式反思 | 上下文连贯 | 模型可能验证自己的错误（"自我确认偏差"） |
| 两步式"生成-反馈" | 不同视角减少偏差 | 额外API成本 |

**关键原则：** 审查Agent只负责"找问题"，不要"重写"——将审查结果反馈给写作Agent修正。

#### 外部反馈(External Feedback)：
- 核心思想：将模型输出在真实环境中执行，根据执行结果（成功/失败、错误信息）迭代修正
- 适用场景：代码执行验证、图表渲染验证、计算验证、JSON Schema验证

**成本优化：** 使用上下文缓存(Context Cache)——缓存命中部分按标准单价20%计费。

---

### 5.6 工作流编排有哪些模式？

**答：**

| 模式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **流水线(Pipeline)** | 固定顺序，每步输出作为下一步输入 | 简单、可预测、易调试 | 刚性，无法处理意外输入 |
| **分支(Branching)** | 路由Agent分析输入，导向不同处理路径 | 比流水线灵活 | 仍为串行 |
| **并行(Parallel)** | 独立子任务同时运行，汇总结果 | 效率高，总耗时=最长子任务 | 要求子任务相互独立 |
| **MoA(混合Agent)** | 多个不同LLM并行处理同一任务(Proposers)，Aggregator综合最佳结果 | 利用模型多样性 | N倍成本 |
| **人机协作(HITL)** | 故意设置暂停节点，交由人类决策/审批 | 建立信任和安全 | 降低自动化程度 |

**成本优化策略：**
- 差异化模型配置（简单任务用便宜模型，关键任务用贵模型）
- 系统化缓存（缓存重复计算）
- 智能批处理（聚合相似请求）

---

### 5.7 Plan & Execute（规划与执行）是什么？

**答：**

**问题：** 固定工作流在遇到意外障碍时会失败（如工具不可用），为每种可能的失败添加异常处理分支不可持续。

**解决方案——Plan & Execute：**
- Agent接收高层目标，动态生成行动计划，然后执行
- 开发者变成"目标设定者"和"能力提供者"
- **目标(Goal) vs 任务(Task)**：固定工作流Agent处理"任务"；规划Agent关注"目标"

**Agent生成计划的两种方式：**
| 方式 | 说明 |
|------|------|
| JSON结构化计划 | 包含step、thought、tool_name、tool_params |
| Code as Action | LLM生成可执行的Python代码，支持变量、条件、循环等复杂逻辑 |

**动态工具创建：** Agent可以使用代码解释器即时创建新工具——编写代码定义、测试、注册新工具函数，然后在后续步骤中使用。

**何时使用自主规划 vs 固定工作流：**
- "先探索再固化"混合策略：对新/不明确的任务使用自主规划Agent发现稳定路径，然后将这些路径固化为固定工作流用于生产。

---

### 5.8 多Agent协作有哪些模式？

**答：**

#### 分层规划模式(Leader-Worker)：
- 集中式星形拓扑，Leader Agent接收顶层任务，分解为子任务分派给Member Agents
- 使用handoff机制实现：Leader将Member Agents视为工具
- **优点**：结构清晰、权责分明，每个子代理拥有独立上下文窗口
- **缺点**：成员之间不直接通信，信息可能延迟或失真
- **适用场景**：目标明确、可清晰分解为并行子任务的场景

#### 共创协作模式(Blackboard)：
- 去中心化，所有Agent围绕共享白板进行头脑风暴
- 使用MsgHub实现：任何Agent的回复自动被其他参与者"听到"
- **优点**：最大化集体智慧，适合开放性创造性问题
- **缺点**：讨论可能发散无法收敛，成本高（3-5倍Token消耗）
- **适用场景**：没有唯一正确答案的开放性、创造性问题

**设计原则：**
- 没有"最佳模式"——设计来自观察人类专家团队的实际工作方式
- 关注：业务流程（依赖 vs 并行）、专家角色（职责）、协作方式（集中 vs 分布）
- 可以混合使用：创意阶段用共创，执行阶段用分层

---

### 5.9 Agent的Memory（记忆机制）有哪些类型？

**答：**

#### 三种记忆管理策略：

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **固定窗口截断** | 只保留最近N轮或N个Token | 简单、低开销 | 可能丢失早期关键信息 |
| **滚动摘要** | 历史接近上限时，用LLM总结最老的部分，替换原始消息 | 保留核心信息，压缩长度 | 额外API成本，摘要质量影响后续对话 |
| **向量化召回** | 将每轮对话存为向量，新查询时做相似度搜索 | 彻底摆脱上下文窗口限制 | 系统复杂度最高 |

**短期记忆 vs 长期记忆：**
| 类型 | 实现 | 用途 |
|------|------|------|
| 短期记忆 | 对话缓冲区 + 截断/摘要策略 | 维持当前会话连贯性 |
| 长期记忆 | 向量数据库 + 工具访问 | 跨会话持久化关键信息 |

**记忆最佳实践：**
- 选择性记忆：不是所有内容都应存储，建立写入阈值
- 持续治理：定期清理过期信息、去重、事实核查
- 场景化：不同业务场景有不同的记忆需求

---

### 5.10 什么是Skill（技能固化）？

**答：**

Skill是将能力固化为可复用流程的模块化能力单元，打包了指令、元数据和可选资源（脚本、模板）。

**从Prompt到Skill的演进（4步）：**
1. 将提示词保存为独立Markdown文件（解决"找不到"）
2. 拆分为主文件+子文件的目录结构（解决"单文件太长"）
3. 分段检查长文档
4. 按需加载——Agent只读取与当前检查阶段相关的子文件（解决"上下文拥挤"）

**Skill与RAG的区别：** RAG检索事实；Skill教"如何做"某事。

**SKILL.md结构：**
- YAML frontmatter：`name`（名称）、`description`（描述，决定何时触发）
- Markdown body：详细指令
- 外部资源文件：详细检查清单、风格指南等，通过链接按需加载

**高质量Skill的五步编写法：**
1. 判断是否值得做（有专家直觉、足够复杂、会被复用）
2. 提取要写什么（专家决策树、反模式，而非仅步骤）
3. 编写好的指令：简洁性、自由度匹配风险级别、渐进式披露、结构化约束（顶层约束不超过7个）
4. 配置工具：可追溯的工作流、反馈循环、高风险操作先验证后执行
5. 验证和迭代："双Agent"模式（Agent A设计，Agent B测试）

### 5.11 如何评测驱动Agent开发？

**答：**

**三条原则：**
1. 评测定义产品能力的上限
2. 能被度量的才能被改进
3. 更快更准的度量反馈带来更好的改进效率

#### 端到端评测：
- 客观指标（规则可执行）：代码可执行性、格式检查、字数限制
- 主观指标（需要语义判断）：内容准确性、教学效果、语言风格
- **关键**：评测指标必须由资深业务专家设计，而非仅技术人员

#### LLM-as-a-Judge：
- 训练/引导另一个LLM扮演"评测专家"
- 将模糊目标拆分为具体的、可检查的项目，逐项判断后汇总分数
- **警惕LLM偏差**：风格偏差、长度偏差、"老好人"偏差、位置偏差
- **最佳实践**：先用人类专家评估建立"黄金测试集"，再校准LLM评测器

#### 白盒评测：
- 进入系统内部，单独评测关键组件
- **优点**：信号清晰（无干扰）、迭代快（测试单组件）、优化精准

#### Skill评测的两个维度：
1. 触发正确性（应该触发/不应该触发）
2. SOP合规性（步骤是否遵循Skill定义）

## 六、生产环境应用实践（16%）

### 6.1 从开发到生产有哪些挑战？

**答：**

| 挑战 | 说明 |
|------|------|
| **成本** | 每次调用大模型API都要花钱。100人同时使用，Token费用可观。能否通过微调小模型降低成本？ |
| **部署** | 系统只在开发机上运行。如何部署到服务器？如何保证高可用？如何监控？ |
| **安全合规** | 用户输入会不会泄露敏感信息？模型会不会输出不当内容？是否符合行业合规要求？ |

### 6.2 模型部署有哪些方案？

**答：**

#### 直接调用API（无需部署）：
- 直接调用预部署模型（如qwen-plus）
- **优点**：无需运维，按Token付费
- **限制**：有QPM/TPM限流，无法使用自定义/微调模型
- **适用**：早期或中小规模场景

#### 测试环境部署（vLLM）：
- vLLM是开源的大模型推理框架，通过CLI简化部署，优化内存和缓存以支持高并发
- **步骤**：下载模型 → 安装vLLM → `vllm serve` 启动服务 → 测试
- 支持OpenAI兼容接口（`/v1/chat/completions`）

#### 云部署方案对比：

| 服务 | 适用场景 |
|------|----------|
| **百炼平台** | 快速部署Qwen系列模型，无需关注基础设施 |
| **函数计算(FC)** | 轻量推理、低频访问、事件触发任务。无服务器GPU，自动扩缩，按需付费。缺点：冷启动延迟 |
| **PAI-EAS** | 标准模型部署，弹性扩缩，蓝绿部署，模型预热。适合实时同步推理 |
| **GPU云服务器(ECS)** | 自定义环境，复杂依赖。无冷启动问题。可结合ESS自动扩缩和SLB负载均衡 |
| **容器服务(ACK/ACS)** | 复杂微服务架构，大规模分布式推理。基于Kubernetes，支持CI/CD |

### 6.3 如何优化大模型应用的性能？

**答：**

**SLO（服务级别目标）关键指标：**
| 指标 | 说明 |
|------|------|
| **TTFT** (Time to First Token) | 首个Token的响应时间 |
| **TPOT** (Time Per Output Token) | 每个输出Token的生成时间 |

**性能优化六招：**

| 招式 | 说明 |
|------|------|
| **1. 更快的请求处理** | 使用更小模型。压缩技术：模型剪枝、量化(INT4/INT8/FP16)、知识蒸馏 |
| **2. 减少请求数和计算量** | 上下文缓存(Context Cache)缓存公共前缀；批推理合并多个请求，闲置资源用于离线推理（50%成本） |
| **3. 减少输入/输出Token** | 输入优化：提取用户意图、生成长文档摘要。输出优化：提示词约束("一句话回答")、`max_tokens`参数 |
| **4. 并行化** | GPU有数千核心，适合矩阵运算。CPU集群无法有效替代GPU。策略：数据并行、模型并行、流水线并行 |
| **5. 不要默认用LLM** | 标准消息用硬编码、有限输入用预计算、图表/分页用经典UI组件、查找用传统算法 |
| **6. 优化用户感知** | 流式输出、分块处理、进度显示、友好错误处理、用户反馈通道 |

---

### 6.4 如何优化大模型应用的成本？

**答：**

**同时提升性能和降低成本的方法：**
- 使用更小模型
- 上下文缓存（缓存命中部分按20%计费）
- 批推理（闲置资源离线推理，50%成本）
- 减少Token数
- 不是所有任务都需要LLM

**GPU实例选择：** 考虑模型参数量、KV Cache使用量、精度设置。例如DeepSeek-R1(671B)需要~625GB显存(FP8)。

**计费方式选择：**

| 计费方式 | 适用场景 |
|----------|----------|
| 包年包月（预付费） | 稳定长期业务 |
| 按量付费 | 不固定时长，灵活需求 |
| 抢占式实例 | 不固定时长，极致成本控制（最高节省90%） |

### 6.5 如何保障大模型应用的稳定性？

**答：**

| 措施 | 说明 |
|------|------|
| **自动扩缩容** | ESS用于ECS/GPU实例，FC按需分配，SLB流量分发 |
| **评测基线管理** | 建立基线模型，定期测试，动态调整基线，自动化部署流水线中加入基线测试关卡 |
| **实时监控告警** | 监控成本（Token消耗）、性能（响应时间 vs SLO）、质量和安全（敏感内容） |
| **容灾** | 降级和熔断机制、跨地域部署、定期故障模拟演练 |

**可观测性（OpenTelemetry）：**
- 开放标准，定义Metrics、Traces、Logs
- ARMS（应用实时监控服务）：云原生可观测平台，兼容OTLP

**三个观测维度：**
| 维度 | 内容 |
|------|------|
| 成本 | 按模型、会话、用户的Token分析 |
| 性能 | 调用链分析，各阶段耗时（检索、Rerank、模型推理） |
| 质量与安全 | 敏感内容检测结果上报 |

### 6.6 大模型应用面临哪些安全威胁？

**答：**

#### 攻击模型本身（5种）：
| 威胁 | 说明 |
|------|------|
| 数据投毒 | 训练数据中植入后门触发器 |
| 数据偏差 | 历史偏见导致歧视性行为 |
| 训练数据隐私泄露 | 模型记忆并可能泄露训练数据中的个人信息 |
| 对抗攻击 | 无关信息干扰模型判断 |
| 模型窃取 | 自动脚本收集问答对克隆模型能力 |

#### 攻击应用（9种）：
| 威胁 | 说明 |
|------|------|
| 提示注入(Prompt Injection) | 注入新指令覆盖模型原始任务 |
| 提示泄露(Prompt Leaking) | 诱导模型泄露System Prompt |
| 幻觉 | 知识库缺乏信息时模型自信地编造答案 |
| 知识库投毒 | 向知识库上传含虚假信息的恶意文档 |
| 谣言放大器 | 模型整合未经验证的互联网搜索结果 |
| 隐私挖掘 | 通过连续查询逐步提取个人信息 |
| 恶意工具使用 | Agent执行危险命令（如`rm -rf *`） |
| 生成式钓鱼 | AI生成专业外观的钓鱼邮件 |
| AI蠕虫 | 邮件系统中的自复制提示词导致无限循环 |

#### 攻击基础设施（2种）：
| 威胁 | 说明 |
|------|------|
| 资源耗尽DDoS | 高计算请求耗尽GPU资源 |
| 云级攻击 | 特权用户威胁、内存转储泄露使用中数据 |

### 6.7 如何构建纵深防御体系？

**答：**

#### 基础设施安全：
- 传统措施：网络隔离(VPC)、系统加固、静态数据加密(KMS)、最小权限(RAM)
- **零信任**："永不信任，始终验证"
- **可信计算**：TPM芯片测量启动链组件，创建可验证的信任链
- **机密计算**：TEE（可信执行环境）在CPU中创建加密隔离的数据处理环境
- **远程证明**：硬件签名的证明报告，验证TEE真实性和软件完整性

#### 应用安全三层实时防御：
| 层 | 措施 |
|------|------|
| 输入过滤 | AI Guardrails安全护栏 |
| 运行时监控 | Agent行为审计 |
| 输出审查 | 内容安全检查 |

#### 高级RAG保护：
- **第一道防线**：知识库访问控制（用户只能检索授权文档）
- **第二道防线**：双重加密——内容加密(AES-CTR-256) + 向量加密(DCPE算法，保持近似距离关系同时防止逆向工程）

#### 合规要求：
| 地区 | 要求 |
|------|------|
| 中国 | 算法备案（《生成式AI服务管理暂行办法》，2023年8月15日起） |
| 欧盟 | AI Act，基于风险的分级监管 |
| 美国 | NIST AI风险管理框架（行业指导，非强制） |

**答：**

**高质量评测集的构建：**

**业务指标与评测指标对齐：**

| 层级 | 示例 | 目的 |
|------|------|------|
| 业务指标 | 用户满意度 > 90% | 最终目标 |
| 核心技术指标 | 召回准确率 > 85%，响应时间 < 2s | 工程度量 |

**持续运营闭环：** 发现问题 → 改进优化 → 跟踪效果 → 迭代指标

### 6.9 意图空间与知识空间的关系是什么？

**答：**

- **意图空间**：所有用户需求/问题的集合
- **知识空间**：知识库中所有知识点的集合

**三个区域：**

| 区域 | 说明 | 优化方向 |
|------|------|----------|
| **重叠区域** | 知识库已覆盖的用户意图 | 优化内容质量和工程算法 |
| **未被覆盖的意图空间** | 用户问了但知识库没有的知识 | 主动补充缺漏知识 |
| **未被利用的知识空间** | 知识库有但用户没问到的内容 | 优化召回算法，剔除无关内容 |

## 七、其他重要知识点

### 7.1 什么是Harness Engineering？

**答：**

Harness Engineering是在不可预测的LLM"引擎"周围构建完整的控制系统，使其可控、可靠、持续改进。

**核心原则：**
1. 仓库知识作为事实来源(System of Record)——QWEN.md是"目录，不是百科全书"
2. 机械化约束执行——linters、CI检查、hooks，而非依赖Agent"自律"

**六层Harness：**
| 层 | 内容 |
|------|------|
| 工具层 | EPCC工作流、审批模式 |
| 上下文层 | /context、/compress、/clear |
| 记忆层 | QWEN.md三级配置 |
| 能力层 | 自定义命令、MCP、Skill |
| 验证层 | 评测驱动的Skill优化 |
| 进化层 | 失败驱动的记忆更新、Skill迭代 |

---

### 7.2 什么是EPCC工作流？

**答：**

EPCC = Explore → Plan → Code → Commit

| 阶段 | 说明 |
|------|------|
| **Explore** | 理解代码库再做修改。添加"只分析，不写代码"约束防止过早编码 |
| **Plan** | 使用Plan Mode生成结构化实施计划。人工审查并迭代计划 |
| **Code** | 按计划逐步执行。每步后审查diff。多文件修改时"每步暂停" |
| **Commit** | 运行测试，自审更改，生成git commit。提交前始终检查暂存文件 |

**四种审批模式：**
| 模式 | 说明 |
|------|------|
| `plan` | 只读分析和规划 |
| `default` | 提出更改但需确认（推荐日常使用） |
| `auto-edit` | 自动批准文件修改，确认命令 |
| `yolo` | 自动批准一切 |

**原则：最小权限——只给Agent刚好够用的自主权。**

---

### 7.3 什么是GraphRAG？

**答：**

GraphRAG结合了RAG和查询聚焦摘要(QFS)：
- RAG擅长精确细节检索
- QFS善于理解总结整体内容
- GraphRAG在处理大规模文本数据时兼具两者优势

---

### 7.4 QwQ模型的特点是什么？

**答：**

- 基于Qwen2.5系列训练的强推理能力模型
- 商业版(qwq-plus)和开源版(qwq-32b)
- 通过强化学习提升数学、代码及通用任务性能
- 核心指标媲美DeepSeek-R1满血版
- 支持超长上下文（131,072 tokens）、多轮对话
- 不支持工具调用、结构化输出等功能
- 适合需要深度思考与高质量回复的应用场景

---

### 7.5 RIDE方法论是什么？

**答：**

RIDE是将AI应用于业务的四阶段框架：

| 阶段 | 英文 | 说明 |
|------|------|------|
| R | Recognize | 选择正确的方向 |
| I | Identify | 设定标准 |
| D | Deploy | 推动实施 |
| E | Evaluate | 验证效果 |

除了技术能力（构建系统），从业者还需要"品味"——选择方向、设定标准、验证结果的能力。

---

### 7.6 Agent的能力边界和反模式有哪些？

**答：**

**Agent擅长的：**
- 代码脚手架搭建
- 阅读/解释代码
- 重复性修改
- 生成测试用例
- 搜索和综合信息

**Agent容易出错的：**
- 过时的API用法
- 项目特定约束
- 跨文件副作用
- 边界条件处理
- 安全敏感操作

**五大反模式：**
1. 一次说太多
2. 不审查diff
3. 忽视上下文膨胀
4. 把Agent当搜索引擎用
5. 不验证就提交
